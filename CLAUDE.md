# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

A static wedding invitation site (Spanish, Camilo & Maritza) built with vanilla HTML, CSS, and JavaScript — no framework, no build step, no package manager.

## Development

No build, lint, or test commands exist. Open the HTML files directly in a browser, or serve the directory with a local static server (`npx serve .`, VS Code Live Server) to avoid any `file://` path quirks.

## Three entry points

- **`index.html`** — the "save the date" teaser: a single non-scrolling section (nav, dots, hamburger menu, and scroll-snap are disabled via inline `<style>`). Loads only `config.js`, `js/countdown.js`, `js/guest.js`, and a small inline `<script>` that fills in the monogram initials, the countdown, and the guest-dependent template text directly — it does **not** load `js/init.js` or `js/common.js`, since those expect sections this page doesn't have. Its inline `<style>` block also redefines the shared CSS custom properties (palette, fonts) from `css/variables.css` with its own values (see `Mockups/Mockup.png`). The page loads behind a full-screen `#cover-screen` tap/click gate (`body.cover-active`); the resulting click is a real user gesture, which the inline script's `openInvitation()` uses to call `.play()` on its own `Audio(WEDDING.audioSrc)` instance — browsers block sound autoplay without one. `index.html`'s texts are hardcoded in its HTML/inline script (only names, date and audio come from `config.js`), unlike `invitacion-completa.html`, where every text is in `config.js`.
- **`invitacion-completa.html`** — the full multi-section invitation, built on `index.html`'s visual design: same palette/fonts (redefined in its own inline `<style>`, not in `css/variables.css`), the same `#cover-screen` gate, hero with monogram, navy background with a cream column, `assets/footer.png` footer and `#scroll-hint` chevron. Loads `config.js`, `js/guest.js`, `js/init.js`, `js/countdown.js`, `js/common.js` (in that order — order matters, see below) and a small inline `<script>` that only handles the cover gate (`openInvitation()` calls `window.startWeddingAudio()`, defined by `js/init.js`) and the scroll hint.

- **`invitacion-libro.html`** — experimental "storybook" version of the full invitation (same content, same `config.js`/`guests.json`). The cover gate is the book's front cover, the sections are the pages (two per leaf, one on each face, see below), and the footer is the back cover (`.back-cover`, under all leaves). Loads `config.js`, `js/guest.js`, `js/init.js`, `js/countdown.js`, **`js/book.js`** — **not** `js/common.js` (it expects `#nav`, `#scroll-progress`, the hamburger and page scroll). Styles are in `css/book.css` (only this page; it redefines the palette/fonts like the other pages do inline). Provides the ids `js/init.js` needs even if unused (`#nav-links` lives inside the bookmark index; `#mobile-menu` is present but `hidden`). Its extra texts are under `WEDDING.book` in `config.js`; the guest name also appears on the cover (`#cover-guest`, filled by `js/book.js` via `getGuestData()`).
  - **Two-sided leaves:** `.book` is an open double-page spread (`2 × --page-w`, spine in the middle). Every `.leaf` sits on the right half and turns over the spine; its `.leaf-front` is a right page and its `.leaf-back` (pre-rotated 180°) is the next left page. Leaf 0 = cover / marbled endpaper; leaf 1 = p1 Prólogo / p2 Ceremonia; leaf 2 = p3 Recepción / p4 Asistencia; leaf 3 = p5 Recomendaciones / p6 Dress Code; leaf 4 = p7 Recuerdos / p8 "Fin". `.back-cover` (p9: footer smoke, signature, "volver a empezar") is fixed on the right half under all leaves. Adding a section means re-pairing faces in the HTML.
  - `js/book.js`: `k` = focused page (0 = cover, odd = right page, even = left page, `LAST` = back cover); leaves turned for `k` = `k === 0 ? 0 : 1 + floor(k/2)`. `faces[k]` maps each page to its element (used for `inert`, `.focused`, fade-in reveal, "desliza ↓", page number and the bookmark index lookup). **Mobile (<900px):** one page is visible and a "camera" (`--cam-x` translate on `.book`, integer px) pans to the focused side; next from a right page turns the leaf while the camera follows it left, next from a left page only pans right (`PAN_MS`), and prev mirrors that. **Desktop (≥900px):** the whole spread is visible and navigation moves one spread at a time (`k` normalized to the odd page; cover centered when closed). Sizes/positions of `.book` and the fixed `.book-hud` (hints, page number, bookmark, arrows, "desliza ↓") are computed in JS (`layout()` / `placeCamera()`), and recomputed on resize/breakpoint change. Input: tap outer 30% of the visible area, swipe, ←/→, dog-ear, hints, bookmark index. Opening the cover calls `window.startWeddingAudio()` once. Idle "peek": the right leaf lifts slightly, or on a left page the camera glances right (`.cam-peek`).
  - `TURN_MS` in `js/book.js` must match `--turn-time` in `css/book.css` (both 1.4s). State classes (`is-cover`, `is-first`, `is-end`, `is-busy`) live on `.book-stage` (it starts with `is-cover` in the HTML so nothing flashes before JS runs). The last turned leaf (`.on-left`) stays visible as the left page; with the 10px mobile gutter a sliver of the neighbouring page always shows. Edge stacks: right `.book-block` shrinks with `--s`, left `.book-block-left` grows with `--r`.
  - **Sharpness:** at rest the focused page is flat (no `preserve-3d`/`backface-visibility`) so it renders at native resolution. Before a turn, `.prep` enables the 3D layer (added on `pointerdown` for the leaf that could turn, and again in `turnLeaf`), and the rotation only starts `PREP_MS` later, so the layer is already rasterized when it starts moving (removes the initial pixelated flash). Uses `setTimeout`, not `requestAnimationFrame`, so timing doesn't stall in background tabs. Perspective is 3600px to limit magnification while turning. Don't move the 3D rules back to the base `.leaf` rule, and avoid `translateX(-50%)` centering on text (use `left:0; right:0; margin:auto; width:max-content`).
  - **Chapters:** each page 2–7 starts with `.chapter-num` (`data-chapter`, filled by `js/book.js` as `WEDDING.book.chapterWord` + roman numeral), `.chapter-title` (`book.chapters.<sectionId>`), a flourish, `.chapter-note` (the section's shared `*.label`, shown as an epigraph) and `.chapter-lead` (`book.leads.<sectionId>`, a short narrator line with an enlarged initial; keep these texts short — the user wants the book to feel light). Page 1 is the "Prólogo" with book-only story texts (`book.onceUpon`, `prologueOpen`, `prologueCouple`, `prologueGuest`, `dateLead`, `countdownLead`); it keeps a `hidden` `#guest-greeting` only because `js/init.js` requires it.
  - **Guest name inside text:** `js/init.js`'s `pick()` replaces `%name%` with the guest name, and a text object may have an `anonymous` variant used when there's no name (no/unknown code). Used by `book.prologueGuest`.
  - Each page scrolls internally if it doesn't fit (`.page-scroll`, with the tiny "desliza ↓" hint); content sizes are compacted under `.leaf …` / `#save-the-date …` selectors in `css/book.css`. All pages fit at 390×720 as of now. The book omits `rsvp.help` on the Asistencia page.

`scriptwd.js` and `styleswd.css` are legacy/unused leftovers not referenced by any HTML file — don't edit them expecting an effect; if touching them, confirm with the user whether they should be deleted.

## Data-driven rendering via `config.js`

For `invitacion-completa.html` and `invitacion-libro.html`, **all** wedding data and **all visible text** (names, date/place, audio, cover, menu labels, hero copy, countdown labels, every section's label/title/details/buttons, recommendations, dress code, QR items) live in the single `WEDDING` constant in `config.js` — this is the only file meant to be edited to re-personalize the invitation. The file header documents the text conventions:
- A text is a string, or `{ single, plural }` when it depends on the guest (see Personalized guest greeting), optionally with an `anonymous` variant used when there is no guest name.
- `\n` = line break, `**bold**` = `<strong>`, `%deadline%` = `WEDDING.rsvp.deadline`, `%name%` = guest name.
- Book-only texts (cover line, hints, prologue, chapter titles/leads, "Fin") live under `WEDDING.book`; everything else (places, times, labels, lists) is shared by both full pages, so editing it changes both.
- `index.html` does not use this text layer (see above).

The HTML is a skeleton with no copy of its own. `js/init.js` fills it using two attributes: `data-t="path.in.WEDDING"` (sets the element's text) and `data-href="path.in.WEDDING"` (sets `href`). It also understands the computed paths `couple`, `groomInitial`, `brideInitial` and `footerSignature`. To add a new text, add the key to `config.js` and an empty element with `data-t` in the HTML. Lists (`#rec-list`, `#dress-grid`, `#qr-grid`) and the nav (`#nav-links`, `#mobile-menu`) are generated entirely by JS. Not in `config.js`: image `src`/`alt`, decorative emoji in dividers, and the dev placeholder labels for missing photos.

## Script responsibilities (`invitacion-completa.html`)

- **`config.js`** — data only (`WEDDING` object). No DOM access.
- **`js/guest.js`** — resolves the `?codigo=` guest code against `guests.json` (see Personalized guest greeting below). Must load before `js/init.js`.
- **`js/init.js`** — populates the whole DOM from `WEDDING` (`data-t` / `data-href`, the big day/month/year and location derived from `weddingDateISO`, nav, lists, greeting) and wires the audio toggle. It renders once immediately with the generic singular version, then calls `getGuestData()` and re-renders the guest-dependent parts (`renderGuest`) when `guests.json` resolves; the nav is built only once because `js/common.js` attaches listeners to it. Also defines `window.startWeddingAudio()`, called by the cover gate. Must load after `config.js` and `js/guest.js`, and **before `js/common.js`**.
- **`js/countdown.js`** — countdown timer reading `WEDDING.weddingDateISO`; self-starts via `setInterval`. Needs the `#cd-*` elements to exist (they are static in the HTML). Must load after `config.js`.
- **`js/common.js`** — UI chrome: section-dot generation/sync (titles come from each section's `data-label`, set by `js/init.js` from `WEDDING.nav`), `IntersectionObserver`-driven fade-in (threshold `0.15`, so sections taller than the screen still reveal) and current-section tracking, scroll-progress bar, hamburger/mobile-menu toggle (binds to the links `js/init.js` generated, hence the load order), image load/error fade-in.

## Section model (`invitacion-completa.html`)

7 sections, each `<section class="section" id="...">` with a `data-section` index. Unlike the original design they are **not** full-viewport and there is no scroll-snapping: the inline `<style>` sets `html, body { scroll-snap-type: none }` and `.section { height: auto; min-height: 0 }` so each section is as tall as its content. Sections are stacked into one continuous cream column over a `#000A19` background; each `.section-inner` has a vertical gradient (odd: `--color-paper` → `--color-paper-dark`, even: reversed) so every section ends with the color the next one starts with — keep that alternation if you add/remove a section. `#save-the-date` holds the first stop flat for 300px so the hero fade blends in. The header `#nav` is hidden at the top of the page and slides in once `js/common.js` adds `.scrolled`.

Each section id is wired into these nav surfaces, all fed from `WEDDING.nav` (`id`, `label`, optional `mobileLabel`, `icon`) — add/remove a section by editing that array plus the `<section>` in the HTML:
- `#section-dots` (generated by `js/common.js` from the live `.section` list; tooltip = `data-label`, set by `js/init.js`)
- Desktop `#nav-links` (generated by `js/init.js`)
- `#mobile-menu` links (generated by `js/init.js`, with the emoji icon)
- Any hardcoded `href="#section-id"` anchor elsewhere in the page

Sections use `scroll-margin-top: 56px` (0 for the first) so anchors clear the fixed header.

## Personalized guest greeting

All three entry points read a `?codigo=XXXX` (or `?code=XXXX`) URL query parameter — never a raw name — and resolve it against `guests.json`, a `{ "CODE": { "name": "Guest Name", "single": true } }` map. `single` marks whether the code was issued to one person (`tú`/singular wording) or a couple/group (`ustedes`/plural wording). `name` can list several people (e.g. `"Deivid, Kate"`). Guests are added/renamed by editing only `guests.json`; no other file needs to change.

`js/guest.js` exposes two functions, both reading the same `guests.json`:
- `getGuestData()` → resolves `{ name, single }`; falls back to `{ name: '', single: true }` (no name, singular wording) whenever the code is missing from the URL or not found in `guests.json`. Used by `js/init.js` (both full pages), `js/book.js` (name on the book cover) and `index.html`'s inline script.
- `getGuestName()` → resolves just the name string (built on top of `getGuestData()`); currently unused by either page.

In `invitacion-completa.html` the guest affects: the greeting `#guest-greeting` (guest name in script font, or `WEDDING.hero.greetingFallback` when there is none) and every `{ single, plural }` text in `config.js`, which `js/init.js` resolves with `single !== false`. To make a new text guest-aware, give it a `{ single, plural }` value in `config.js`; no HTML/JS change is needed.

`js/guest.js` must load before `js/init.js` (`invitacion-completa.html`) or before the inline script (`index.html`) that calls these functions. Because it uses `fetch()`, this requires the site to be served over `http(s)://` — a local static server or the deployed host — it will not resolve when an HTML file is opened directly via `file://`. This is the only dynamic runtime input on the site; there is no backend or client-handled form submission — RSVP and memory-sharing links (`WEDDING.rsvp.formLink`, `WEDDING.qrs.items[].link`) just open external URLs.

## CSS structure

Split across `css/variables.css` (color palette, fonts, spacing custom properties — edit here for a palette/typography change), `css/common.css` (nav, mobile menu, scroll progress, dots, footer, audio toggle), `css/sections.css`, and `css/components.css`. All four are loaded by all three HTML entry points; `invitacion-libro.html` additionally loads `css/book.css` (book-only, no inline `<style>`). `index.html` and `invitacion-completa.html` override the palette/fonts and several layout rules (`.section`, `.section-inner`, footer, header) in their own inline `<style>` with `!important` where `css/sections.css` needs beating — prefer editing the inline block of the page you are changing over `css/*.css`, which affects both pages.

## Asset convention

Images live in `assets/`. Decorative rose corner images (`rosas-tl.png`, `rosas-tr.png`, `rosas-bl.png`, `rosas-br.png`, `rosas-b.png`) are placed per-section as ordinary `<img class="corner-img ...">` tags directly in the HTML — they are not injected by JavaScript. In `invitacion-completa.html`, sections are stacked with no gap, so **don't put a bottom rose on a section when the next one has a top rose on the same side** (they would meet at the boundary); the last section (`#qrs`) has no bottom roses at all because the footer smoke covers them. `WEDDING.audioSrc` gates background audio: set to `null` to disable it, or to a file path to enable it — currently set to `assets/background.mp3`. In `invitacion-completa.html` `js/init.js` creates the player, drives the `#audio-toggle` button, and exposes `window.startWeddingAudio()` for the cover gate's click; in `index.html` it drives its own separate tap-to-open `Audio` instance. `assets/mainPicture.png` is the hero image of both pages (already fades to the background color at the bottom edge). `assets/footer.png` (1024×491) is a dark, cloud-textured image with a transparent cutout at its top, used as the `<footer class="teaser-footer">` background on both pages — the transparent cutout lets the page background show through, so it reads as smoke rising into the footer rather than a hard rectangle. In `invitacion-completa.html` the footer sits in `.footer-wrap` (navy background) and is capped at the 680px column with `aspect-ratio: 1024 / 491`, so on wide screens the image isn't stretched to the window width; it overlaps the end of `#qrs` via a negative `margin-top`, which is why `#qrs .section-inner` has extra bottom padding. `assets/foto1.png` (beach) is used in Recuerdos; `foto5.png`/`foto6.png` are currently unused. `foto1.png`–`foto4.png` are only ~528px wide, so on high-density phone screens they look soft; that can only be fixed by replacing them with larger files (≈900px+), not in code. In the book, the back cover reuses `footer.png` as `.back-footer`.
